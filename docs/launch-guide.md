# Launch Guide: Closed Beta

This guide takes vibepost from the current state of the repository to live
online. The code is closed-beta ready: invite-gated multi-user accounts,
per-user data isolation, guided onboarding, a privacy policy page, and a
single-container production build. What remains is configuration and
infrastructure — roughly an afternoon of work.

## What the code now provides

- **Accounts**: passwordless by default — sign in with a single-use emailed
  link (15-minute expiry, hash stored only) or a WebAuthn passkey; a password
  (bcrypt) is optional. Sessions in httpOnly `SameSite=Lax` cookies (Secure
  flag in production), 7-day expiry, login/signup rate limiting.
- **Transactional email**: sign-in links sent via Resend. Without an API key
  (local development), links are printed to the server log instead.
- **Invite-gated signup**: tokens are generated by an admin (UI or CLI), stored
  only as SHA-256 hashes, single-use, expiring (14 days by default).
  The **first account created becomes the admin** — sign up first.
- **Per-user isolation**: profiles, channels, posts, media, and platform
  credentials (Meta/LinkedIn app keys) are all scoped to the owning account.
  Cross-user access returns 404.
- **Onboarding wizard**: new users are walked through creating a profile and
  connecting Bluesky (2 min), Meta, Threads, and LinkedIn (bring-your-own
  developer app during beta, per `roadmap/architecture.md`), with copyable
  OAuth redirect URIs.
- **Account lifecycle**: change password, JSON data export (GDPR portability),
  hard-delete with full cascade (rows, media files, scheduled jobs, session).
- **Operations**: `/api/health` endpoint, scheduler job recovery after restart
  (overdue posts publish immediately rather than silently never), production
  mode disables API docs and adds HSTS/security headers.

## Step 1 — Decide the deployment shape

The intended shape for the beta is **one Fly.io machine, one volume**
(SQLite + uploads on the volume, FastAPI serving the built frontend).
`fly.toml` and the root `Dockerfile` implement this. The Supabase/R2/Postgres
architecture in `roadmap/architecture.md` is the post-beta target; nothing in
this guide forecloses it.

> ⚠️ Run **exactly one machine**. SQLite and the in-process scheduler do not
> tolerate multiple instances (`fly scale count 1`).

## Step 2 — Create the Fly app

```sh
fly launch --no-deploy          # accept the existing fly.toml when prompted
fly volumes create vibepost_data --size 3 --region yul   # match primary_region
```

Pick the region close to your beta users; note the data-residency point in
`roadmap/privacy.md` (you can move a Fly volume later more easily than a
Supabase project, but still: choose deliberately).

## Step 3 — Set secrets

```sh
fly secrets set SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(48))')"
fly secrets set OAUTH_CALLBACK_BASE="https://YOUR-DOMAIN"
fly secrets set FRONTEND_URL="https://YOUR-DOMAIN"
fly secrets set RESEND_API_KEY="re_..." EMAIL_FROM="vibepost <login@YOUR-DOMAIN>"
```

The app refuses to boot in production without `SECRET_KEY`. Rotating it logs
everyone out (sessions are signed with it) but loses no data.

For the email secrets: create a free Resend account (resend.com), add your
domain under Domains, and publish the SPF and DKIM DNS records it shows you
(do this alongside the Fly DNS records in the next step). Sign-in links are
emailed through Resend; without these secrets nobody can log in by email in
production, so treat them as required. Accept Resend's DPA while you're in
their dashboard.

Passkeys need no configuration: the WebAuthn relying-party id is derived from
`FRONTEND_URL`. Note that passkeys are bound to your domain — ones registered
during local development won't work in production, and vice versa.

## Step 4 — Point the domain at Fly

```sh
fly certs add YOUR-DOMAIN
```

Then at your DNS provider, add the `A`/`AAAA` records (or `CNAME` for a
subdomain) that `fly certs add` prints, and wait for the certificate to be
issued (`fly certs show YOUR-DOMAIN`). `force_https = true` is already set.

## Step 5 — Deploy

```sh
fly deploy
fly logs        # watch it boot; hit https://YOUR-DOMAIN/api/health
```

## Step 6 — Claim the admin account and invite your beta

Admin rights are only ever granted from the server console — signup order
grants nothing.

1. Generate the first invite from the server console:
   ```sh
   fly ssh console -C "python -m app.manage invite new --note 'founder'"
   ```
2. Sign up at `https://YOUR-DOMAIN` with that invite (no password needed —
   you'll sign in by emailed link, and can add a passkey in Settings).
3. Promote yourself:
   ```sh
   fly ssh console -C "python -m app.manage promote you@example.com"
   ```
4. Create further invites from **Settings → Beta Invites** in the UI (or the
   CLI). Tokens are shown once; send each invitee theirs privately.

If you have data in a pre-auth local database you want to keep, copy it onto
the volume and attach the old single-tenant rows to your account:

```sh
fly ssh console -C "python -m app.manage claim-orphans you@example.com"
```

## Step 7 — Platform apps (beta policy: bring your own)

Per the beta workaround recorded in `roadmap/architecture.md`, each beta user
creates their own free Meta/LinkedIn developer apps; the onboarding wizard
walks them through it and shows the exact redirect URIs to register
(`https://YOUR-DOMAIN/api/auth/{meta,threads,linkedin}/callback`). Bluesky
needs no developer app — just an app password.

Before the **public** launch (not needed for the beta): create the shared
vibepost Meta app and start Meta App Review well in advance, ditto LinkedIn.

## Step 8 — Pre-launch obligations checklist

From `roadmap/privacy.md`, adapted to the beta architecture:

- [x] Privacy policy at a stable URL — served at `/privacy`, linked from
      sign-up, the sidebar, and account deletion. **Review the text once more
      before inviting strangers** (it currently lists your contact email).
- [x] Account deletion flow implemented and tested end-to-end
- [x] Data export (portability) implemented
- [ ] Accept the Fly.io DPA (dashboard → organization settings)
- [ ] Accept the Resend DPA (dashboard) — Resend processes user email
      addresses and sign-in mail on our behalf
- [ ] Configure log retention: Fly keeps logs briefly by default; do **not**
      attach a log shipper, or if you do, set 7-day retention
- [ ] Verify backups: `fly volumes snapshots list <volume-id>` — Fly takes
      daily snapshots automatically; confirm they exist after a day. For
      belt-and-braces, occasionally `fly ssh sftp get /data/vibepost.db`.
- [x] Transactional email implemented (Resend): sign-in links double as
      password recovery — a forgotten password is a non-event, just sign in
      by email. Post-failure email notifications remain a nice-to-have
      (failures are visible in the queue UI).

## Step 9 — Smoke test the live instance

1. Sign up with an invite, complete onboarding, connect Bluesky.
2. Schedule a post 5 minutes out; confirm it publishes (times are stored UTC
   and shown in your local timezone).
3. `fly machine restart` while a post is scheduled; confirm it still
   publishes (job recovery).
4. Export your data; delete a test account; confirm its media is gone from
   `/data/uploads`.

## Known beta limitations (accepted, documented)

- **Media URLs are public-but-unguessable** (`/media/<uuid>`): Instagram and
  Threads require fetching media from a public URL, so media of *scheduled*
  posts is reachable by anyone holding the exact URL until the post is
  deleted. UUID filenames make guessing infeasible. The post-beta R2 +
  presigned-URL design (`roadmap/media-privacy.md`) closes this.
- **Sign-in is only as strong as the user's mailbox** (true of any service
  with email-based recovery): magic links are single-use, expire in 15
  minutes, are stored only as hashes, and require a button click on the
  landing page (so inbox link-scanners can't consume them) — but a fully
  compromised mailbox means a compromised vibepost account. Passkeys don't
  remove that floor while email sign-in remains available; it's the industry-
  standard trade-off.
- **Single machine**: a Fly hardware failure delays scheduled posts until the
  machine is restored from snapshot. Acceptable for beta.
- **Sessions are stateless JWTs** with a per-user epoch: deleting an account
  or changing the password immediately invalidates every outstanding session
  for that user. There is no per-device "log out that one session" — changing
  the password is the revocation tool.
- **Platform credentials are stored unencrypted in SQLite** on the volume
  (the Vault design in `roadmap/security.md` is post-beta). Treat volume
  snapshots and `fly ssh` access accordingly.

## Post-beta roadmap pointers

The migration path to the target architecture is documented in
`roadmap/architecture.md` (Supabase Postgres + Auth + Vault, R2 media,
passkeys, Stripe). None of this blocks the closed beta.
