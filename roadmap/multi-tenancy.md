# Multi-tenancy, Auth, and Deployment

## Direction

Move from a single-user local tool to a properly multi-tenant web app:
- Each user has their own profiles, channels, posts, and credentials
- Professional auth (not HTTP basic)
- User secrets (platform API keys) encrypted at rest
- Deployed on infrastructure that scales automatically with zero manual intervention

---

## Recommended Stack

### Supabase — database, auth, file storage, secrets vault

Supabase is a managed Postgres platform with several features that directly solve
the problems here.

- **Postgres** replaces SQLite; supports concurrent users and is required for the
  job store when running multiple backend instances
- **Supabase Auth** handles sign-up, sign-in, email verification, password reset,
  and social OAuth (Google, GitHub, etc.) out of the box; issues standard JWTs
- **Row Level Security (RLS)** enforces data isolation at the database level —
  users literally cannot query each other's rows even if the app has a bug
- **Supabase Storage** replaces the local `uploads/` directory; handles media
  files with access control and a CDN
- **Supabase Vault** stores user platform credentials (Meta App Secret, LinkedIn
  Client Secret, etc.) encrypted with a server-managed key; app reads them via a
  Postgres function, they never appear in plaintext in application queries
- CLI: `supabase` — migrations, local dev stack, secrets, all scriptable

### Fly.io — backend compute

Fly.io runs Docker containers directly (we already have a Dockerfile).

- Scales to zero between requests; scales out automatically under load
- Machines are billed per second of actual CPU use
- Global deployment (pick regions) with minimal config
- CLI: `flyctl deploy` — one command to ship a new version
- Persistent volumes available if needed (not needed once Supabase handles storage)
- `fly.toml` config file lives in the repo

### Cloudflare Pages — frontend

Build the React app in CI, deploy the static output to Cloudflare Pages.

- Free tier is generous; global CDN with no config
- CLI: `wrangler pages deploy dist/`
- Or connect the GitHub repo and it deploys automatically on push

## Architecture Changes Required

### 1. Database: SQLite → Postgres

- All SQLAlchemy models carry over; change the engine URL to Postgres
- Add `user_id` (foreign key to `auth.users`) to `Profile`, `Channel`, `Post`,
  `AppSetting`
- Write RLS policies so each row is only visible to its owner
- Replace APScheduler's in-memory job store with the SQLAlchemy Postgres job store
  so scheduled posts survive restarts and work across multiple backend instances

### 2. Auth: add JWT middleware to FastAPI

- Supabase Auth issues JWTs signed with the project's JWT secret
- FastAPI verifies the token on every request (a small middleware, ~30 lines)
- `user_id` is read from the verified token and threaded into all DB queries
- No session table needed; tokens are stateless

### 3. Secrets: Supabase Vault

- User platform credentials (Meta App Secret, LinkedIn Client Secret, etc.) are
  currently stored as plaintext JSON in the `channels` table
- Move them into Supabase Vault; store only a vault secret ID in the `channels` row
- The backend reads the decrypted value via `vault.decrypted_secrets` at query time
- The encryption key never leaves Supabase's infrastructure

### 4. File storage: Supabase Storage

- Replace the `uploads/` directory and `/media/` static route with Supabase Storage
- Upload goes directly from the browser to a presigned URL (removes the backend
  from the upload hot path entirely)
- Access control: private bucket, signed URLs generated by the backend per request

### 5. Scheduler: multi-instance safe

- Switch APScheduler to use `apscheduler.jobstores.sqlalchemy.SQLAlchemyJobStore`
  pointed at Postgres with a `coalesce=True` / `max_instances=1` policy
- Only one instance executes a given job even if multiple backend pods are running

## Migration Path

Keep local dev working throughout:

1. Add `supabase` local stack to `docker-compose.yml` (it spins up Postgres, Auth,
   Storage, and Vault locally via Docker)
2. Migrate models and add `user_id` — existing single-user data can be assigned to
   a seed user
3. Add auth middleware behind a feature flag so the app stays usable while it's
   being wired up
4. Move secrets to Vault last, once the rest is stable
